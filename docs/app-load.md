# Прикладная нагрузка и сырые данные (M-07)

`tools/wsload` сохраняет запланированные операции и наблюдаемую доставку.
Режим `-fixture` использует зарегистрированных пользователей и приватные чаты
между разными gateway. Прежний режим синтетических пользователей сохранён
для воспроизведения старых опытов; он не доказывает доставку другому участнику.

`tools/e2e -load` подготавливает настоящие пары через регистрацию, MailHog,
верификацию и login, запускает wsload и собирает логи. Для каждой комбинации
профиля и транспорта создаётся новый изолированный стек с пустыми БД,
Redis, NATS и MinIO. Тестовые данные не используют volumes приложения.

## Команды

Из корня репозитория, подготовка без Docker:

```sh
make app-load-prepare E2E_WORK_DIR=out/app-load
```

Команда собирает пять сервисов, `e2e` и `wsload`, выпускает сертификаты
и фиксирует хеши исходников/бинарников/сертификатов. Функциональная E2E
использует тот же комплект; прежние комплекты требуют повторной подготовки.

Следующая команда **запускает Docker** и короткие проверки инструмента:

```sh
make app-load-run E2E_WORK_DIR=out/app-load
```

По умолчанию — девять независимых стеков: три профиля × `grpc`, `grpc-tls`,
`quic`. На стек — восемь пар (16 настоящих пользователей), 4 операции/с,
прогрев 1 с, измерение 4 с, наблюдение после нагрузки 2 с, seed 1.
Порядок фиксирован для приёмки инструмента; это не основная серия.

Один профиль и транспорт:

```sh
make app-load-run E2E_WORK_DIR=out/app-load \
  LOAD_FLAGS='-transport grpc-tls -load-profile messages -load-pairs 20 -load-rate 10 -load-warmup 5s -load-duration 30s -load-drain 15s -load-seed 7'
```

Профили:

| Имя | Измеряемая операция | Задействованные RPC |
| --- | --- | --- |
| `messages` | Отправка через WS, ACK, доставка и `notify_push` получателю на другом gateway | оба gateway → chat, worker → chat/auth |
| `auth` | CreateChat уже существующей приватной пары, проверка прежнего chat ID | chat → auth |
| `media` | RequestUpload → PUT MinIO → ConfirmUpload → download URL для другого участника → GET и проверка байтов | media → chat |

Полезные байты вложений передаются по HTTP в MinIO. QUIC и gRPC в этом
сценарии обслуживают межсервисные проверки прав и метаданных.

Файлы по умолчанию — 64 КиБ (`-load-media-bytes`). Это непрозрачные тестовые
данные, клиентское шифрование не выполняется. Участники подключены к WS,
но не посылают `set_active`: для notification-worker они неактивны.
Внешние браузерные Web Push endpoints не вызываются.

До измерения runner ждёт HTTP-сервисы, NATS-consumers и регистрацию всех
WS-сессий. Подготовка аккаунтов и чатов не входит в измерение. Приватный JSON
с токенами имеет права 0600 и удаляется после дочернего процесса; в сырых
результатах нет JWT, паролей, presigned URL или содержимого вложений.

## Планирование, ошибки и границы наблюдения

Нагрузка open-loop: пуассоновское расписание определяется seed и gateway,
новые операции не ждут ответов. Пары выбираются по кругу. Сетевые запросы
на одной WS-сессии записываются в порядке расписания. Дедлайн каждой
операции по умолчанию 10 с **от запланированного момента**, включая очередь
генератора. Несовместимая/неполная фикстура завершается ошибкой до нагрузки.

Ограничены незавершённые операции (`-max-inflight`, по умолчанию 10 000)
и очереди записи по сессиям. Переполнение записывается как `not_sent`,
не меняет расписание и не исчезает из знаменателя. Запись WS с ошибкой
закрывает сессию, чтобы последующие ответы не были приписаны чужому запросу.
Сообщения и файловые операции не повторяются автоматически.
HTTP-профиль auth обращается к уже существующей паре и проверяет её ID.

Дедлайн после отправки WS — наблюдаемый предел клиента. Он не отменяет
уже отправленную операцию на сервере: поздний ACK и уведомление сохраняются
отдельно, терминальный исход `deadline` не заменяется успехом. Успешный
ACK после дедлайна может сопоставить доставку, но не делает операцию
успешной в срок. Пустое поле времени означает отсутствие наблюдения;
ноль — допустимое смещение от начала прогона.

После отправок выдерживается полное окно drain. Пропуск означает отсутствие
сопоставленного события в этом окне, а не доказанную потерю навсегда.
Для итогового сравнения дедлайнов drain должен быть не меньше тайм-аута
операции. У `no_response` поле `latency_ns` — нижняя граница ожидания,
а не время получения ответа; такие цензурированные результаты требуют
отдельного учёта. Короткий drain по умолчанию служит проверке инструмента.

Порядок проверяется между сообщениями одного отправителя одному получателю
внутри чата; между независимыми отправителями порядок расписания не считается
порядком фиксации транзакций. Доставка может предшествовать ACK.

SIGINT/SIGTERM позволяет сохранить отменённые и ещё не отправленные операции.
При отмене до запланированного времени `complete_ns` может быть меньше
`scheduled_ns`: это не измерение отрицательной задержки, а отменённая будущая
операция. Такой прогон имеет `failed.json` и не имеет completion marker.
SIGKILL, авария диска и убийство хоста не гарантируют сохранения данных.

## Артефакты

Каталог: `out/app-load/load-runs/<ID>-<transport>-<profile>/`.

| Путь | Содержимое |
| --- | --- |
| `report.json` | Статус подготовки/нагрузки/очистки, ревизия и prepared manifest |
| `meta.json` | Completion marker всего стека; появляется после логов и успешной очистки |
| `load.log`, `services.log` | Вывод генератора и логи только своего стека |
| `load/calls.csv` | Одна строка на каждую запланированную операцию, включая прогрев и неотправленные |
| `load/deliveries.csv` | Одна ожидаемая доставка на каждую запланированную отправку сообщения |
| `load/events.csv` | Все наблюдаемые `message_received` и `notify_push`, включая дубли и несопоставленные события |
| `load/metrics-start-N.prom`, `load/metrics-end-N.prom` | Граничные снимки RPC-метрик, очередей и остальных метрик пяти HTTP endpoints |
| `load/resources.json` | Docker CPU/RAM/сеть, CPU ядер и генератора, реальные времена снимков и параметры окружения |
| `load/meta.json` | Завершённый экспорт wsload; при его сбое вместо него `failed.json` |

Каталоги и файлы приватные (0700/0600). Существующий каталог результата
не перезаписывается. Готовность всего прогона определяет внешний `meta.json`,
а не наличие CSV или внутреннего completion marker.

`calls.csv`: `operation_id`, `step` (-1 для прогрева), `gateway`, `kind`,
`user_id`, `peer_id`, `chat_id`; времена `scheduled_ns`, `deadline_ns`,
`send_ns`, `response_ns`, `complete_ns`; терминальные `outcome`/`error`,
фактические `response_outcome`/`response_error`, `latency_ns`, `useful_bytes`.
Смещения — **наносекунды по монотонным часам одного процесса**, от начала
прогрева. Запланированное расписание одно и то же для всех транспортов
при одинаковых параметрах и seed; ID аккаунтов и технических прогонов различаются.

Исходы: `success`, `rpc_error`, `write_error`, `connection_closed`,
`deadline`, `not_sent`, `no_response` (наблюдение закончено до дедлайна).
Число строк равно `planned`; `planned`/`pending` не остаются терминальными
исходами. Поздний ответ сохраняет `response_ns` и фактический исход ответа.
Для HTTP media одна строка описывает составную операцию целиком; этапы
не выдаются за отдельные независимые вызовы.

`deliveries.csv` связывает операцию с получателем, ACK ID и received ID;
содержит времена первого получения/notify, accepted, дубли и нарушения
порядка/идентичности. Неподтверждённое уведомление не пропадает из `events.csv`,
даже если его пока невозможно сопоставить с отправкой. Собственная копия сообщения отправителю также остаётся в `events.csv`,
но не входит в доставку другому участнику и имеет пустой `operation_id`.
Тела сообщений туда не записываются. Пустой `operation_id` события означает отсутствие сопоставления.

Метаданные содержат `media_bytes` и `kind_names` (порядок индексов массива
`mix`), все исходы измерения, параметры, полезные байты и goodput
проверенных скачиваний, завершённых внутри окна измерения (байт/с).
Текстовая таблица сохраняет прежние перцентили **только успешных ответов**
и отдельно печатает исходы всех запланированных операций. Для итогового
анализа нужны CSV: ошибки нельзя исключать из задержек и знаменателей.

## Ресурсы и границы выводов

Снимки контейнеров читаются через локальный Unix socket Docker API только
для собственного project `wisply-load-*`. Сохраняются image IDs, memory/CPU
limits, cpuset, разрешённые runtime-настройки, кумулятивное CPU-время в нс,
текущая RAM и счётчики сетевых байтов всех 13 контейнеров, включая зависимости.
Нулевой ресурсный лимит означает отсутствие ограничения. Полный environment
контейнеров не выгружается. Docker через TCP/SSH этим коллектором не поддержан.

Два снимка задают реальное окно для разности CPU-счётчиков; у каждого есть
целевой момент, времена запроса и `engine_read`. Границы Docker, HTTP-метрик
и расписания не атомарны. Каждый Prometheus-файл содержит комментарии
`wsload_snapshot_before_unix_ns` / `wsload_snapshot_after_unix_ns` с фактическими
границами HTTP-чтения. Расхождение видно в артефактах и должно учитываться
при калибровке. RAM — два наблюдения, не пик. Сброс счётчиков делает сбор
ресурсов неуспешным. CPU генератора и всех логических ядер сохраняется в
тиках `/proc`; их частота определяется `getconf CLK_TCK`. Поля CPU ядра:
user, nice, system, idle, iowait, irq, softirq, steal, guest, guest_nice.
Guest уже входит в user/nice; при суммировании его нельзя учитывать дважды.

CPU ядер включает фоновые процессы и ядро, поэтому не приписывается одному
сервису. Сохраняются Go, ядро Linux, архитектура, число CPU и доступные
сетевые настройки хоста; они не подменяют настройки namespaces контейнеров.
Эти короткие прогоны работают без закрепления CPU и без сетевых воздействий.
Они проверяют инструментарий, а не преимущество транспорта.

Основное сравнение — gRPC TLS против QUIC; plaintext gRPC остаётся отдельным
контролем. Численная матрица, повторы, ресурсы и калиброванные сетевые профили
основной серии фиксируются отдельно по [методике](rpc-comparison.md).
Ни успешная техническая проверка, ни один короткий p99 не дают вердикта.
Данные этого формата не смешиваются со схемой библиотечного стенда.


## Локальная проверка 15 ноября 2026

Окончательная версия прошла девять комбинаций на одной подготовке исходников,
бинарников и сертификатов (базовая ревизия `5dd2162`, незакоммиченный код
идентифицируется `source_sha256`). В каждой комбинации сохранены все
18 запланированных операций: 3 прогрева и 15 измерения. Все **135 операций
измерения успешны**; расписания совпадают между транспортами для каждого
профиля. Все ожидаемые доставки получателю и notify наблюдались, без дублей,
перестановок и несовпадений ID. Media проверила точное совпадение 64 КиБ.

Отчёты в `out/app-load/load-runs/` (в каждом каталоге — `report.json`,
внешний `meta.json`, `load/` и логи):

| messages | `4ab421747df0-grpc-messages` | `162a46a88351-grpc-tls-messages` | `0913c5e41a3f-quic-messages` |

Проверены совпадение prepared manifests и текущих хешей файлов, число
и уникальность строк, времена отправки/ответа/дедлайна, все исходы,
назначенный получатель, права 0600, удаление временных токенов, по два
снимка всех 13 контейнеров и временные отметки HTTP-метрик. Это проверка
схемы и работы инструментов; основной сравнительной серией она не является.
