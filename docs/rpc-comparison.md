# Прикладное сравнение транспортов Wisply (M-06)

Основное сравнение — **`grpc-tls` против `quic`** на одинаковой версии
приложения. `grpc` без TLS остаётся отдельным контролем цены шифрования.
Его результат нельзя выдавать за изолированную разницу TCP и QUIC.
Существующие таблицы README относятся к старому коду и plaintext gRPC;
пилот библиотеки и данные приложения анализируются отдельно.

## Реализованные контроли

| Условие | gRPC TLS | QUIC |
| --- | --- | --- |
| Клиентский режим | `grpc-tls` | `quic` |
| Сервер auth/chat в Compose | TCP 50052 | UDP 50051 |
| TLS | 1.3 | 1.3 |
| Группа обмена ключами | `X25519MLKEM768` | `X25519MLKEM768` |
| Сертификаты | CA и сертификат сервиса из `quic-certs` | те же файлы |
| Проверка сервера | CA, срок действия, имя в адресе | то же |
| Авторизация | JWT / внутренний секрет | те же interceptors |
| Прикладные обработчики | сгенерированный grpc-go API | тот же API через `grpcbridge` |
| Метка метрик / трасс | `grpc-tls` | `quic` |
| Прокси из окружения | отключены для межсервисных клиентов | прямое соединение |

TLS-порт auth/chat задаётся `GRPC_TLS_PORT`, сертификат и ключ —
существующими `QUIC_CERT_FILE` / `QUIC_KEY_FILE`. Клиентам нужны
`CHAT_SERVICE_TLS_ADDR` / `AUTH_SERVICE_TLS_ADDR` и `QUIC_CA_FILE`.
В Compose эти значения заданы; адреса для plaintext/QUIC остаются прежними.
Локальный grpc-gateway и health probe используют прежний TCP listener 50051
одинаково для всех вариантов. Это отдельный локальный участок пути запроса.

Один экземпляр каждого клиента содержит одно соединение к сервису назначения
(без пула). Число клиентов фиксируется числом экземпляров сервисов: два
gateway, по одному auth/chat/media/worker. Не включаются 0-RTT и mTLS.
gRPC TLS сохраняет настройки grpc-go и лимит запроса chat 256 КиБ.
QUIC сохраняет собственные окна, лимит активных потоков и keepalive.
Обмен ключами согласован, но алгоритмы управления перегрузкой, flow control,
пингования и реализация RPC различаются; их нельзя считать выровненными.
Размеры нагрузки должны укладываться в меньший лимит всех вариантов.

## Схема прогонов

Основная единица анализа — независимый прогон. Транспорты запускаются
**последовательно в отдельных стеках**, с одинаковыми бинарниками и
сертификатами. Одновременное A/B на общих БД, Redis, NATS и ядрах годится
только для диагностики: нагрузка одного варианта влияет на другой.

Перед каждым прогоном создаются новые БД, пустые Redis/NATS/MinIO и один и тот
же набор тестовых пользователей, чатов и файлов. Подготовка и проверка
готовности не входят в окно измерения. Прогрев выполняет тот же сценарий
с той же интенсивностью; его результаты исключаются из измерения.
Исходное состояние одинаково, но накопление сообщений внутри прогона
остаётся частью выбранного сценария. Для разных интенсивностей — новые
прогоны, а не последовательные ступени на одной выросшей БД.

Порядок тройки транспортов меняется по шести перестановкам с фиксированным
сидом; все три используют одинаковый сид нагрузки в пределах повтора.
Порядок, сиды и все попытки сохраняются до запуска. Ошибки, перегрузка
и неуспешные прогоны сохраняются; выборочный повтор ради красивого числа
недопустим. Число повторов и предел времени фиксируются в плане серии
до сбора её данных, с учётом общего бюджета стенда и приложения.

Ресурсы фиксируются одинаково для каждого варианта: CPU/memory limits,
GOMAXPROCS, cpuset, число экземпляров, образы и их digest, параметры БД,
размеры пулов БД, очереди fanout, версии Go/ядра, настройки сокетов и offload.
Изменение лимита ресурса образует отдельную конфигурацию. Нельзя сравнивать
ограниченный Docker CPU одного варианта с неограниченным другим.
Генератор нагрузки и зависимости учитываются отдельно от RPC-сервисов.

## Нагрузки и наблюдения

Для предварительной калибровки существующий `tools/wsload` поддерживает:

| Профиль | Доли операций | Начальные интенсивности |
| --- | --- | --- |
| Чтения | presence 50%, read status 50% | 100 и 200 запросов/с суммарно |
| Сообщения | presence 45%, read status 45%, send 10% | 100 и 200 запросов/с суммарно |

Для каждого gateway — 200 пользователей. Начальные окна: прогрев 15 с,
измерение 60 с, наблюдение после отправок 15 с. Это калибровка, а не основная
серия и не основание для вердикта. Пример одного профиля на одном транспорте:

```sh
cd tools/wsload
GOWORK=off go run . \
  -gateways gateway-1=ws://localhost:8080/ws,gateway-2=ws://localhost:8081/ws \
  -users 200 -steps 100 -warmup 15s -step 60s -drain 15s \
  -mix get_presence=45,get_read_status=45,send_message=10 -seed 1
```

Секрет JWT должен совпадать с **отдельным тестовым стеком**. Предварительно
оба gateway и остальные клиенты этого стека выбирают один транспорт.
Проверяются фактические метки успешных RPC; одного имени варианта недостаточно.

Текущий wsload использует синтетические токены и чаты пользователя с собой.
Он различает ACK и собственное `message_received`, но не измеряет доставку
другому участнику и не создаёт репрезентативную нагрузку на все пять связей.
Сквозной E2E проверяет эти связи функционально, но не является open-loop
генератором. До основной серии M-07 должен добавить сырые результаты
и сценарий с настоящими парами пользователей на разных gateway,
обращениями к auth, уведомлениями и отдельными media-операциями.
Доли этих операций фиксируются в плане после калибровки, до основных данных.

Задержки считаются от запланированного времени, отдельно до ACK и доставки.
Сохраняются запланированные/отправленные/ошибочные/неотвеченные операции,
пропуски, дубликаты и порядок. Ошибки нельзя исключать из знаменателя
или маскировать низким p99 успешных ответов. Для media дополнительно нужны
полезные байты и goodput; для сервисов и зависимостей — CPU, память,
очереди и время запросов. Один p99 гистограммы Grafana не заменяет сырые данные.

Для основной серии медианы и перцентили получают по отдельным прогонам,
интервалы — bootstrap по прогонам. Процентили разных прогонов не объединяются
усреднением. Задержки перегруженного варианта показываются вместе с долями
ошибок и ростом очередей, без обычного вывода о преимуществе по задержке.
Пороги перегрузки, семейства сравнений и достаточное число повторов должны
попасть в исполнимый план M-07/M-08 до основной серии; правила библиотеки
автоматически не переносятся на отличающуюся прикладную нагрузку.

## Сеть и ограничения существующих инструментов

Нужно различать две постановки:

1. Воздействие только на gateway ↔ chat — объясняет этот участок, остальные
   связи остаются в обычной сети.
2. Воздействия на все пять межсервисных связей — проверяет распределённый
   сценарий; каждому направлению нужны явно заданные правила и счётчики.

Существующий `scripts/netem.sh` реализует только первую постановку. Фильтр
по IP охватывает и новый TLS-порт, но скрипт не ограничивает полосу и
не создаёт обрывы. Он меняет TSO/GSO на контейнерных eth0 и GRO на концах
veth хоста, а при `off` задаёт Docker defaults, не восстанавливает снимок
прежних значений. Использовать его на проде для этой серии не предусмотрено.
Для основной серии нужны сохранение/восстановление фактических значений
и самостоятельная проверка воздействий, а не предположение по команде tc.

В план входят обычная сеть, RTT без потерь, RTT с потерями, ограниченная
полоса и обрыв. Полоса должна ограничивать только выбранные RPC, одинаково
в двух направлениях; совместное ограничение всех TCP/UDP-потоков одной
связи не должно выдавать отдельный бюджет каждому транспорту.
Момент и длительность обрыва задаются относительно окна измерения.
TSO/GSO/GRO, QUIC GSO, qdisc, очереди и счётчики потерь фиксируются для
каждого участка; склейка пакетов меняет смысл вероятности потери netem.
Численные профили и их допуски утверждаются до основной серии.

E2E использует иной механизм: односторонняя задержка ответов 50 мс + 1%
потерь либо blackhole на source port 50051/50052 в собственных auth/chat
namespaces. Он проверяет корректность и восстановление, без калибровки
RTT/полосы и без изменения offload хоста. Эти отчёты не являются замером
прироста транспорта.

## Границы готовности

M-06 даёт работающий зашифрованный контроль и постановку прикладного сравнения.
M-07 — исполнимый план, сырые данные, полный генератор и измерение ресурсов.
M-08 — согласованные реальные серии и разбор результатов.
Локальный Docker и целевые хосты — отдельные наборы данных с собственными
характеристиками сети и ресурсов. Успешная локальная проверка не подтверждает
прирост или свойства production-сети. Длинные серии и действия на проде
выполняются отдельной согласованной задачей.
