# Сквозная проверка Wisply (M-05)

Инструмент `tools/e2e` проверяет реальное приложение с `grpc` и `quic` на всех
пяти межсервисных связях. Для каждого транспорта создаётся отдельный Compose
project `wisply-e2e-<случайный ID>-<транспорт>`. Варианты идут последовательно.
Это проверка корректности и восстановления; её длительности не являются
сравнительными замерами производительности.

## Подготовка без Docker

Из корня репозитория на Linux:

```sh
make e2e-test
make e2e-prepare
```

`e2e-test` запускает тесты инструмента с HTTP/WebSocket-заглушками и подставным
исполнителем команд. Он не вызывает Docker и не запускает существующие
repository integration-тесты с testcontainers.

`e2e-prepare` компилирует пять сервисов и runner через `CGO_ENABLED=0`, создаёт
тестовый CA и сертификаты существующим `scripts/quic-certs.sh`. Docker, сборка
образов и запуск контейнеров в этой команде отсутствуют. Нужны Go из go.mod
и OpenSSL; при отсутствии зависимостей Go может скачать их обычным способом.

Результат — игнорируемый `out/e2e/` (или `E2E_WORK_DIR`): бинарники,
сертификаты и `prepared.json` с ревизией, временем подготовки, хешем исходников
и SHA-256 бинарников/сертификатов. Изменение исходников или подготовленных
файлов требует повторной подготовки; устаревший комплект не допускается к
запуску. Один commit hash не описывает незакоммиченные изменения, поэтому
сохраняется также хеш содержимого исходников.

## Запуск с Docker

**Следующая команда запускает Docker.** Выполнять после отдельного решения
поднять стенд:

```sh
make e2e-run
# Либо один вариант:
make e2e-run E2E_FLAGS='-transport quic'
```

Нужны Docker Engine и `docker-compose` с поддержкой Compose profiles и
`depends_on.condition`, Linux network namespaces, доступ к Docker daemon.
Runner собирает маленький образ `wisply-e2e-netem` из существующего
`scripts/netem.Dockerfile`; сервисы используют подготовленные host-бинарники
в `alpine:3.20`, без пяти Go builder-образов. Остальные образы — версии
Postgres/Redis/NATS/MailHog/MinIO из основного Compose. Сборка production-образов
этим запуском не проверяется.

Данные трёх БД, NATS и MinIO находятся в tmpfs тестовых контейнеров. Redis
не сохраняет данные. Нет внешних volumes, фиксированных имён контейнеров,
публикации БД и доступа к существующим данным приложения. HTTP-порты и NATS
monitoring доступны на случайных портах `127.0.0.1`. Grafana, Jaeger, nginx
и реальная SMTP/Push-инфраструктура не поднимаются. На время запуска нужна
оперативная память для БД/объектов в tmpfs; обычный файловый кеш образов Docker
всё равно занимает место на диске.

После запуска runner сначала ждёт auth/chat/media, затем notification-worker,
затем оба gateway и их JetStream-consumers. События не публикуются до готовности
потребителей `DeliverNew`. Старта HTTP listener недостаточно для этой проверки.

## Сценарии

1. Три настоящие регистрации, получение кода через MailHog, верификация и login.
   Создание чата вызывает `chat → auth`; два участника подключаются к разным
   gateway, третий пользователь остаётся посторонним.
2. Отказы без авторизации и запрет чужой истории/загрузки файлов.
3. Отправка в обе стороны: ACK, `message_received`, ID, содержимое, отправитель,
   порядок, пропуски и дубликаты. История сверяется с отправками; посторонний
   пользователь не получает события чата.
4. Редактирование, прочтение, удаление сообщения и удаление отдельного group chat.
5. RequestUpload → PUT MinIO → ConfirmUpload → скачивание другим участником;
   точное совпадение байтов и запрет скачивания посторонним.
6. Проверка успешных клиентских RPC по `/metrics` с выбранным `transport`:
   оба gateway → chat, chat → auth, media → chat, worker → chat/auth.
7. Доставка при задержке ответов 50 мс и потерях 1%.
8. Дедлайн и явная отмена клиентского HTTP-запроса, который проходит через
   chat → auth, при блокировке ответов auth.
9. Блокировка RPC-ответов chat дольше 10-секундного дедлайна gateway,
   восстановление сети и проверка результата записи через историю.
10. Плавный и аварийный перезапуск auth, затем chat. Существующие WebSocket
    сессии должны снова отправлять сообщения через оба gateway.
11. Итоговая сверка всех записей с неопределённым исходом и проверка живости.
    После обоих перезапусков chat повторно проверяются media upload/download
    через существующий клиент, notify_push и новый успешный worker → auth RPC.

При неопределённом исходе `send_message` отправляется **один раз**. После
восстановления runner проверяет историю: допустимы ноль или одна сохранённая
копия; успешный ACK требует одной копии с тем же ID. Уведомления во время
сбоя могут отсутствовать, что записывается отдельно. Итоговая сверка после
перезапусков помогает заметить поздние дубли. Ошибочный результат не повторяется
ради успешного теста. Для готовности повторяются чтения истории и метрик;
после перезапуска auth — также идемпотентный CreateChat для уже существующей
пары с проверкой прежнего ID (он проходит через переиспользуемый chat → auth
клиент). Число попыток готовности сохраняется; send_message не повторяется.

Notification-worker проверяется через `notify_push` и успешный RPC
`ListPushSubscriptions`. Пользователь подключён к WS, но не посылает
`set_active`, поэтому для worker он offline. Браузерные push-подписки не
регистрируются: доставка во внешний Web Push endpoint здесь не проверяется.
Ключи и тела сообщений — непрозрачные тестовые значения; клиентское шифрование,
OAuth, password reset и UI также не входят в эти сценарии.

## Воздействия и границы выводов

`netem` ставится только на `eth0` тестового auth/chat контейнера, для ответов
с source port 50051 (TCP и UDP). Управляющий HTTP, БД, Redis, NATS и клиентский
WebSocket идут без этих воздействий. Инструмент не меняет offload или qdisc
реального хоста и не использует host network. Контейнер инструментов получает
`NET_ADMIN` только в выбранном network namespace.

Это односторонние пробы корректности, **не** воспроизведение профилей основного
стенда: полоса, RTT в обоих направлениях, offload и точность потерь не калибруются.
Потери случайны; такой запуск не служит основанием для вывода о приросте QUIC.
При перезапуске сервисного контейнера воздействие уже снято. После stop/start
runner заново узнаёт случайный опубликованный HTTP-порт сервиса. Правила снимаются
также при ошибке пробы; завершение запуска удаляет весь его отдельный project.

Перезапуск chat совмещается с попыткой отправки, но конкретное попадание
процессного сигнала между записью в БД и ответом не детерминировано. Сценарий
blackhole отдельно создаёт определённое окно неопределённого ответа.

## Результаты

В `out/e2e/runs/<ID>-<transport>/` сохраняются:

- `report.json`: ревизия, хеши подготовки, транспорт, время начала/окончания,
  исход и длительность каждого сценария в миллисекундах, наблюдаемые потери,
  дубликаты и порядок. Статусы `not_run`, `failed`, `passed` различаются.
- `services.log`: логи только созданного тестового project.

JSON обновляется после каждого сценария. `passed=true` появляется только
после всех проверок, сбора логов и удаления тестового project. Первый сбой
останавливает зависимые сценарии этого транспорта; другой транспорт запускается
отдельно, если общий контекст не отменён. SIGINT/SIGTERM запускают сбор логов
и очистку своего project. При SIGKILL runner не может выполнить cleanup;
имя project имеет вид `wisply-e2e-<ID>-<transport>` и совпадает с каталогом
результатов с добавлением префикса. Данные tmpfs исчезнут при удалении контейнеров.

Пропуски и дубликаты наблюдаются в ограниченном окне (`-observe`, по умолчанию
1 секунда); отсутствие поздних событий за пределами запуска не доказывается.
Проверка HTTP-дедлайна относится к клиентскому наблюдению; длительность работы
серверного обработчика после отмены отдельно не измеряется.

CI запускает только тесты инструмента без Docker. Пройденные unit-тесты,
компиляция и разбор YAML не заменяют реальную приёмку: M-05 закрывается лишь
после успешных сквозных прогонов и разбора обнаруженных проблем.

## Локальная приёмка 8 ноября 2026

Полный запуск после исправлений завершился успешно: **14/14 сценариев gRPC
и 14/14 QUIC**, включая очистку обоих тестовых projects. Рабочая ревизия до PR —
`632fcfe`; точное содержимое собранного кода зафиксировано в prepared manifest
и каждом отчёте, так как изменения этого PR на момент проверки не закоммичены.

Отчёты в локальном `out/e2e/runs/`:

- `2890bda3ca64-grpc/report.json`;
- `918ab42bcba5-quic/report.json`.

В обычном обмене на обоих gateway: missing=0, duplicates=0, out_of_order=0.
При blackhole на обоих транспортах ACK завершился ошибкой, сообщение оказалось
в истории в единственном экземпляре, а уведомление отсутствовало на обоих
клиентах. Это соответствует текущей best-effort политике; успешная приёмка
не означает гарантированной доставки. Итоговый аудит не нашёл повторных
записей после обрывов и перезапусков; media и worker также проверены повторно
после рестартов через существующие RPC-клиенты.

Реальный запуск обнаружил отсутствующую реализацию AuthService.Health
(HTTP 501); она добавлена, регрессионный HTTP-тест проверяет оба транспорта.
В самом инструменте исправлены запрос конфигураций NATS-consumers, минимальный
состав group chat и обновление случайных опубликованных портов после stop/start.
Неуспешные диагностические прогоны сохранены отдельно и не выдаются за успешные.

Это локальная проверка корректности. Удалённый CI, production Dockerfiles,
внешний Web Push и сравнительная серия производительности здесь не подтверждены.
