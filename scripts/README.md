# Backup / restore

Бэкап и восстановление для трёх Postgres-баз (`auth`, `chat`, `media`).
Оба скрипта выполняются на **хосте**, не внутри контейнера — они дёргают
`docker exec` у уже запущенных `*-db` контейнеров.

## Backup

```bash
scripts/backup.sh
```

Дампит все три базы через `pg_dump`, гзипует каждую в
`$BACKUP_DIR/<db>-<UTC timestamp>.sql.gz` (дефолт `BACKUP_DIR`:
`/root/messenger-on-go-backups`), затем удаляет дампы старше
`$RETENTION_DAYS` дней (дефолт `14`) из этой директории.

Переменные окружения (все опциональны):

| Переменная | Дефолт | Что делает |
|---|---|---|
| `BACKUP_DIR` | `/root/messenger-on-go-backups` | Куда пишутся дампы |
| `RETENTION_DAYS` | `14` | Дампы старше этого срока удаляются при каждом запуске |
| `COMPOSE_PROJECT` | `messenger-on-go` | Префикс имени compose-проекта для имён контейнеров (`<project>-auth-db-1` и т.д.) — менять нужно, только если деплоили под другим именем проекта |

### Cron

Добавить в crontab деплой-юзера (`crontab -e`) на прод-сервере — запускает
бэкап ежедневно в 03:00 по времени сервера:

```
0 3 * * * cd /root/messenger-on-go && ./scripts/backup.sh >> /var/log/messenger-backup.log 2>&1
```

Проверить, что реально работает: `tail -f /var/log/messenger-backup.log`,
либо `ls -la /root/messenger-on-go-backups` после первого запланированного
запуска.

Копирование вне сервера здесь не реализовано — `$BACKUP_DIR` это всё ещё
локальный диск того же VPS, так что от потери всего сервера это не спасает.
Направьте cron на директорию, синхронизируемую куда-то ещё (rclone/rsync в
облачное хранилище и т.п.), если это важно для вашего деплоя.

## Restore

```bash
scripts/restore.sh <auth|chat|media> <путь-к-дампу.sql.gz>
```

**Деструктивно** — удаляет и пересоздаёт схему `public` в этой базе перед
загрузкой дампа, то есть всё, что там было, пропадает. Перед выполнением
просит ввести имя базы для подтверждения.

Пример:

```bash
scripts/restore.sh chat /root/messenger-on-go-backups/chat-20260916T030000Z.sql.gz
```

После восстановления сервис, владеющий этой базой, подхватывает
восстановленные данные при следующем запросе — рестарт не требуется
(проверено локально: media-service остался healthy во время реального
drop+restore схемы, без прерывания работы).
